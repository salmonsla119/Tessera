게임 규칙은 [GDD.md](GDD.md) 참조. 이 문서는 **어떻게 만들 것인가**만 다룬다.

## 1. 확정된 기술 결정

| 항목 | 결정 | 근거 |
|---|---|---|
| 멀티플레이 | **비동기 턴제 온라인** (체스닷컴 데일리 방식) | 실시간 동기화 부담 없이 PvP 성립 |
| 서버 권위 | **전면 권위 서버** | 주사위·회피가 승패를 직접 좌우하므로 클라 신뢰 불가 |
| 클라이언트 | **Phaser 3** + TypeScript + Vite | 전투 연출 |
| 서버 | Node + Fastify + Prisma + Postgres | 규칙 엔진(TS)을 그대로 재사용 |
| 패키지 관리 | pnpm 워크스페이스 모노레포 | 규칙 엔진을 클라·서버가 공유 |

> 현재 작업 폴더의 `HANDOFF.md`, `CondTable.cs`, `EffectTable.cs` 등은 **HIGH NUM**이라는 별개 Unity 프로젝트의 데이터 계층이다. 이 프로젝트와 코드·데이터를 공유하지 않는다.

## 3. 규칙 엔진 (`packages/rules`)

### 3.1 공개 계약

```ts
createMatch(deckA, deckB, seed): MatchState
legalActions(state, playerId): Action[]
applyAction(state, action): { state: MatchState, events: GameEvent[] }
```

### 3.2 설계 원칙

- **순수 함수 + 불변 상태.** 렌더링·네트워크·전역 상태 없음. `Phaser`, `document`, `fetch`를 import하지 않는다.
- **난수는 시드에서만.** `Math.random()` 금지. 같은 `(초기 상태, 액션 로그)`는 항상 같은 결과를 낸다.
- **이벤트 반환.** `applyAction`은 애니메이션용 이벤트 배열을 함께 반환한다:
  `PieceMoved` · `SkillUsed` · `DiceRolled` · `Evaded` · `Damaged` · `PieceDown` · `TurnEnded`
  Phaser는 **이 이벤트만 보고 연출한다.** 상태를 직접 읽어 계산하지 않는다.

> 이 분리가 계획 전체의 핵심이다. Phaser 프로젝트의 가장 흔한 실패는 씬 코드 안에 규칙이 스며드는 것이고, 그렇게 되면 서버 검증·자동 대전·리플레이가 전부 불가능해진다.

### 3.3 구현 순서

의존성이 낮은 것부터. 각 단계마다 테스트를 먼저 쓴다.

```
rng → ap → state → movement → targeting → damage → actions → resolve → sim
```

## 4. 서버 (`apps/server`)

### 4.1 이벤트 소싱

- `match_actions`는 **append-only**.
- 상태 = `초기 상태 + 액션 로그 리플레이`. N개마다 스냅샷 캐시.
- 리플레이·관전·분쟁 검증이 부수적으로 따라온다.

### 4.2 권위 원칙

- 클라이언트가 보낸 액션은 서버가 `legalActions`로 **재검증한 뒤에만** `applyAction`.
- **모든 주사위는 서버에서 굴린다.** 클라가 보낸 주사위 결과는 무조건 무시.
- `GET /matches/:id`는 요청자 시점으로 **미공개 정보를 마스킹**한다. 배치 공개 전에는 상대 덱 구성과 배치 좌표를 **응답에서 아예 제거**한다 — 보내놓고 UI에서 가리는 방식은 개발자 도구로 뚫린다.

### 4.3 API

| 엔드포인트 | 용도 |
|---|---|
| `POST /queue` | 덱을 지정해 매칭 큐 등록 (성사되면 즉시 매치 반환) |
| `GET /queue` | 내 대기 상태 + 현재 대기 인원 |
| `DELETE /queue` | 큐 취소 (멱등 — §5.6) |
| `POST /matches/private` | 초대 코드 발급 (친구 대전) |
| `POST /matches/private/:code/join` | 초대 코드로 참가 |
| `GET /matches` | 내 진행 중 매치 목록 (내 턴 여부·남은 시간) |
| `GET /matches/:id` | 내 시점 상태 + 이벤트 로그 |
| `POST /matches/:id/deploy` | 배치 제출 |
| `POST /matches/:id/actions` | 액션 제출 |
| `GET /decks`, `POST /decks` | 덱 CRUD (서버에서 예산 재검증) |

### 4.4 테이블

`users` · `decks` · `match_queue` · `matches` · `match_actions` · `match_snapshots`

```
match_queue(
  user_id       PK,          -- PK로 두어 중복 등록을 DB 레벨에서 차단
  deck_snapshot jsonb,       -- 등록 시점의 덱 사본 (§5.2)
  rating        int,
  joined_at     timestamptz
)
```

## 5. 매칭 시스템

### 5.1 비동기 매칭의 전제

실시간 게임의 매치메이킹과 근본적으로 다르다.

- 상대가 **접속해 있을 필요가 없다.** 큐에 등록해두고 브라우저를 꺼도 된다.
- "상대 찾음 → 10초 안에 수락" 핸드셰이크가 필요 없고, 따라서 수락 거부(닷지) 페널티도 필요 없다.
- 매칭 성사 = 양쪽 매치 목록에 새 매치가 생기는 것. 상대는 나중에 접속해서 발견한다.

따라서 **큐 테이블 + 원자적 페어링**만으로 충분하다. 실시간 매치메이커 서버나 WebSocket 상시 연결이 필요 없다.

### 5.2 큐 등록 — `POST /queue { deckId }`

1. **동시 진행 매치 상한 확인** — 기본 10개. 초과 시 거부한다. 비동기라 매치가 무한정 쌓일 수 있다.
2. 덱 유효성 재검증 — 예산 30, 최대 6기물, 존재하는 베이스·스킬 ID.
3. **덱을 스냅샷해서 큐 행에 저장한다.** 대기 중에 덱을 수정해도 등록된 큐에는 영향이 없다. "등록할 땐 A덱이었는데 매칭되니 B덱" 문제를 원천 차단한다.
4. 페어링 시도(§5.3) → 성공하면 매치를 반환, 실패하면 큐에 넣고 대기 상태를 반환.

### 5.3 페어링 — 등록할 때 즉시 시도

새로 들어온 사람이 **기존 대기자를 집어가는** 방식. 별도 워커 없이 이것만으로 대부분 해결된다.

```sql
BEGIN;

SELECT * FROM match_queue
 WHERE user_id <> :me
   AND user_id NOT IN (:최근_대전_상대)   -- 직전 상대 재매칭 회피
 ORDER BY joined_at ASC                   -- FIFO: 오래 기다린 사람 우선
 LIMIT 1
 FOR UPDATE SKIP LOCKED;                  -- ★ 핵심

-- 찾으면: 두 큐 행 DELETE + matches INSERT
-- 못 찾으면: 내 행 INSERT

COMMIT;
```

`FOR UPDATE SKIP LOCKED`가 이 시스템의 핵심이다. A와 B가 동시에 등록하면서 둘 다 대기자 C를 집으려 할 때, 락을 잡지 못한 쪽은 C를 **건너뛰고** 다음 후보를 본다. 이게 없으면 C가 두 매치에 동시 편성되거나 트랜잭션이 서로 물려 대기한다.

### 5.4 스위퍼 — 안전망

큐가 빈 상태에서 A와 B가 **정확히 동시에** 등록하면, 둘 다 "대기자 없음"을 보고 각자 INSERT한다. 서로 매칭됐어야 할 두 명이 나란히 대기하게 된다. 드물지만 실제로 발생한다.

→ **10초 주기 스위퍼**가 대기 목록을 FIFO로 훑어 짝을 지어 준다. §5.7의 레이팅 창 확장도 이 스위퍼가 담당한다.

### 5.5 매칭 성사 시

하나의 트랜잭션 안에서 처리한다.

1. 두 큐 행 삭제
2. `matches` 생성 — 양측 덱 스냅샷 복사, **매치 시드**(암호학적 난수) 생성, 상태 `deploying`
3. **선공 결정** — 매치 시드로 양측 d20 굴림, 동점 시 재굴림
4. 양측이 배치 단계로 진입

이후 진행은 [GDD §8](GDD.md) 참조.

### 5.6 큐 취소 — `DELETE /queue`

**멱등이어야 한다.** 취소 요청과 매칭 성사가 동시에 일어날 수 있다. 이미 매칭된 뒤라면 에러가 아니라 **성사된 매치를 반환**한다. "취소를 눌렀는데 에러가 나고 매치는 생겨 있는" 상태를 만들면 안 된다.

### 5.7 레이팅 매칭 (M4)

MVP는 FIFO만 쓴다. 레이팅 도입 시:

- 단순 Elo (K=32), 신규 1200
- 매칭 창: 시작 ±100 → 대기 30초마다 ±50 확장 → 5분 후 제한 해제
- 창 확장 판정은 스위퍼(§5.4)가 담당한다

### 5.8 친구 대전

`POST /matches/private`로 초대 코드를 발급하고, 상대가 `POST /matches/private/:code/join`으로 참가한다. 큐를 거치지 않고 매치를 직접 만들며, 레이팅에는 반영하지 않는다.

### 5.9 대기 상태 표시

`GET /queue` → `{ status, joinedAt, waitingCount }`

즉시 매칭을 기대하지 않게 만드는 것이 중요하다. `대기 중 · 현재 N명 대기 · 매칭되면 매치 목록에 표시됩니다` 형태로 안내하고, **창을 닫아도 대기가 유지된다**는 점을 명시한다.

## 6. 클라이언트 (`apps/web`)

씬 흐름: `Boot` → `Menu` → `DeckBuilder` → `Queue` → `Deploy` → `Battle` → `Result`

`Menu`는 **매치 목록이 중심**이다. 비동기라 여러 판이 동시에 진행되므로, 내 턴인 매치를 상단에 모으고 각 매치의 남은 제한시간을 함께 보여준다. `Queue`는 대기 화면이며 폴링으로 성사를 확인한다.

- **덱빌더는 Phaser 캔버스가 아니라 HTML/CSS 오버레이로 만든다.** 리스트·필터·드래그가 있는 폼 UI를 Phaser로 짜는 것은 비용 대비 손해다. Phaser는 보드와 전투 연출만 담당한다.
- 공격 전 예상 데미지 범위는 클라이언트가 `packages/rules`의 `damage.ts`를 **직접 호출**해 표시한다. 같은 코드이므로 서버와 결과가 어긋나지 않는다. 확정 결과는 서버 응답으로 덮어쓴다.

|---|---|---|

## 8. 검증

### 8.1 규칙 엔진 (M0, 매 커밋)

```bash
pnpm --filter rules test
```

| 테스트 | 기대값 |
|---|---|
| AP 이월 골든 | 속도합 27 → `2, 3, 3, 2, 3, ...` (GDD §2.3 표와 일치) |
| AP 불변성 | 기물이 죽어도 `teamSpeed`가 변하지 않음 |
| 데미지 파이프라인 | ATK 5 + `pierce`(2~7) → 거리1 `7~12`, 거리3 `5~8` |
| 이동 | 직선/대각 경로 차단, L자 도약, 보드 밖·아군 칸 제외 |
| 회피 상한 | EVA 80인 기물의 실효 회피율이 60%로 클램프됨 |
| 결정론 | 같은 시드 + 같은 액션 로그를 두 번 리플레이 → 최종 상태 동일 |
| 코스트 | 예산 초과 덱 / 7기물 덱 / 미등록 스킬 ID 덱이 전부 거부됨 |

### 8.2 헤드리스 자동 대전 (M0 직후 — 가장 중요)

```bash
pnpm --filter rules sim -- --games 1000
```

측정 항목: 무한 루프 발생 여부 · 평균 턴 수 · 선공 승률 · 40턴 서든데스 발동 비율 · 기물별 생존율 · **승리 팀의 AP가 단일 기물에 몰린 비율**(§9-1).

여기서 조정할 밸런스 노브: 거리 감쇠 배율 · 회피 상한 · 후공 보정 · 코스트 테이블.

### 8.3 클라이언트 (M1~M2)

로컬 핫시트로 실제 1판 완주. dev 서버를 띄우고 브라우저에서 확인.

### 8.4 매칭 시스템 (M3 — 동시성 테스트가 핵심)

매칭 버그는 부하가 걸릴 때만 드러나므로 **반드시 동시 요청으로** 검증한다.

| 테스트 | 방법 | 기대값 |
|---|---|---|
| 대량 동시 등록 | 빈 큐에 100개 계정이 `POST /queue` 동시 호출 | 정확히 50매치 생성, **한 계정이 두 매치에 편성되는 경우 0건**, 큐 잔여 0 |
| 홀수 등록 | 101개 동시 등록 | 50매치 + 큐 잔여 정확히 1명 |
| 대기자 쟁탈 | 대기자 1명 상태에서 2명이 동시 등록 | 1매치 생성 + 큐 잔여 1명 (`SKIP LOCKED` 동작 확인) |
| 취소 경합 | 매칭 성사와 `DELETE /queue`를 동시 발생 | 에러 없이 매치가 반환됨 (§5.6 멱등성) |
| 중복 등록 | 같은 계정이 두 번 `POST /queue` | 두 번째는 거부 또는 기존 대기 반환. 큐에 행 2개가 생기지 않음 |
| 자기 자신 매칭 | 한 계정이 큐에 있는 상태에서 재등록 시도 | 자기 자신과 매칭되지 않음 |
| 덱 스냅샷 | 등록 후 덱 수정 → 매칭 | 매치에는 **등록 시점** 덱이 들어감 |
| 매치 상한 | 활성 매치 10개인 계정이 등록 | 거부 |
| 스위퍼 | 큐에 2명을 직접 INSERT (페어링 우회) | 10초 내 자동 페어링 |

### 8.5 서버 일반 (M3)

## 9. 밸런스 리스크 (M4 이전에 데이터로 확인)

1. **단일 기물 AP 몰빵** — 기물당 횟수 제한이 없으므로 강한 기물 하나에 매 턴 AP를 전부 쏟는 전략이 성립한다. 이동 패턴이 제한적이라 단독으로 파고든 기물은 포위당하기 쉽다는 점이 자연스러운 억제 장치이지만, 시뮬레이션에서 "한 기물이 AP의 70% 이상을 소비한 승리"가 지배적으로 나오면 억제책(같은 기물 연속 공격 시 SP 코스트 증가 등)을 검토한다.
2. **원거리 카이팅** — 감쇠가 약하면 원거리가 일방적 우위, 강하면 원거리 자체가 무의미. 감쇠 배율과 스킬 사거리를 함께 조정해야 한다.
3. **선공 어드밴티지** — 후공 +0.5 이월이 충분한지 시뮬레이션으로 확인.
4. **비동기 매치 길이** — 6기물 전멸이 조건이라 한 판이 수십 턴이 될 수 있고, 24시간 턴 제한과 곱해지면 실제로 몇 주가 걸린다. 평균 턴 수가 목표(30턴 내외)를 넘으면 보드를 6×8로 줄이거나 HP를 낮춘다.
